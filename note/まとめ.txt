===========================================================
HALシネマ AIチャットボット機能 発表用まとめ
===========================================================

【1. 全体像】

チャットボットは目的別に2つに分かれている（別ファイル・別画面）。

  ① AIアシスタント（html/chatbot.html）
     → お問い合わせ専用。ログイン不要。
     → 例：「上映時間は？」「駐車場ある？」等の質問に回答するだけ。
     → 予約や映画データの取得は行わない（純粋な会話のみ）。

  ② AIチャットボット（html/ai-chatbot.html）
     → 「AIおすすめ映画」「AI予約」専用。ログイン必須。
        未ログインでアクセスすると自動的にログイン画面へ飛ばされる
        （js/ai-chatbot-guard.js）。
     → 上映中の全ページ上ナビに「AIチャットボット」リンクがある。

最初にどちらのモードで開いたかに応じて、選べる機能が変わる。
①は「アシスタント」しか無いので選択肢を出さずに即会話開始、
②は「おすすめ映画」「AI予約」の2択を最初に選ばせる。

会話1回ごとの流れ：
  ブラウザ（js/chatbot.js）
    → POST /api/chat  { intent, messages, slots }
    → backend/internal/chat/handler.go が intent ごとに処理を振り分け
    → 返り値 { reply, messages, slots, recommendedMovies?, uiAction? }
    → 画面に返信を表示、必要なら座席ピッカー等のUIを描画

DeepSeek（外部AI API）を使うのは「会話文の生成・意図の読み取り」だけ。
座席選択・予約確定・二重予約防止といった「お金と席が関わる処理」は
DeepSeekを一切介さず、サーバー側で決定的（if文で確実）に処理する。
＝AIにお金の計算や予約確定を"喋らせない"設計。

-----------------------------------------------------------

【2. AIおすすめ映画（intent = "recommend"）】

やっていること：
  1. ログイン確認（未ログインなら「ログインしてください」で終了）
  2. DBから現在上映中の映画一覧を取得
  3. DBからその会員の過去の予約履歴を集計し、よく見るジャンルを取得
  4. 上記2つをDeepSeekに渡して「おすすめ・理由」を生成させる
  5. DeepSeekが返したおすすめ映画IDが、実在する映画IDかチェックしてから
     （＝AIが存在しない映画をでっち上げても弾く＝ハルシネーション対策）
     ポスター付きカードで画面に表示

取得しているデータ（DBテーブル）：
  ・t_MOVIE + t_MOVIE_IMAGE
      → 上映中（f_is_showing=1）の映画のタイトル・ジャンル・上映時間・
        年齢区分・あらすじ・ポスター画像URL
  ・t_RESERVATION + t_SCHEDULE + t_MOVIE（JOIN）
      → その会員（f_member_id）が過去に予約した映画のジャンルを集計し、
        件数が多い順に上位3ジャンルを取得（＝簡易パーソナライズ）
        新しい専用テーブルは作らず、既存の予約実績だけで実現している

カードには「AI予約で進める」「詳細・通常予約」ボタンがあり、
そのままAI予約フローや通常の作品詳細ページへ接続できる。

-----------------------------------------------------------

【3. AI予約（intent = "reserve"）】

チャット上で座席選択～決済まで完結できる。会話は次の順番で進む：

  ① 映画を選ぶ
  ② 人数を伝える
  ③ 日にちを選ぶ（今週7日間の中から、上映がある日だけ提示）
  ④ その日の上映時間（上映回）を選ぶ
  ⑤ 座席を選ぶ（座席選択だけはDeepSeekを使わず、
     既存の座席選択ページと同系統のボタン式グリッドUIをその場で表示）
  ⑥ 支払い方法を選ぶ（保存カード／QRコード決済／窓口支払い）
  ⑦ 予約確定 → 予約番号・QRコードチケットを発行

ポイント：
  ・③④⑤⑥⑦のように「情報が既に決まっている場面」は全部サーバー側で
    決定的に処理し、DeepSeekを呼ばない。DeepSeekを呼ぶのは
    「次に何を聞けばいいか分からない・自由文から情報を抜き出したい」
    という場面だけ（映画名の聞き取り、人数の聞き取り等）。
  ・DeepSeekが読み取った内容（slots）は、そのままDBに保存せず、
    実在チェック（映画IDが存在するか等）をしてからマージする。
  ・予約確定処理（finalizeReservation）は、Web版の通常予約と全く同じ
    CreateReservation関数を共通で呼び出している。
    → つまりAI予約もWeb予約も「同じ二重予約防止ロジック」を通る。

取得・使用しているデータ（DBテーブル）：
  ・t_MOVIE            … 予約対象の映画一覧
  ・t_SCHEDULE + t_SCREEN + t_SEAT_STOCK
      … 指定した映画の「今週7日間」の上映回一覧と、各回の残席数
        （空席数 = t_SEAT_STOCKのf_stock_status=0の件数を集計）
  ・t_SEAT + t_SEAT_STOCK
      … 座席選択画面用に、座席番号と現在の空席／予約済み状態を取得
  ・t_SCREEN_PRICE + t_PRICE_CATEGORY
      … 座席の料金（一般料金で統一・チャット予約では区分選択なし）
  ・t_MEMBER_CARD
      … 会員が登録済みのクレジットカード一覧（支払い方法の選択肢）
  ・t_RESERVATION / t_RESERVATION_DETAIL / t_TICKET
      … 予約確定時にINSERT。予約1件（複数座席でも）につき
        チケット（QRコード）は1枚だけ発行

【4. ダブルブッキング（二重予約）対策】

一番の要は t_SEAT_STOCK テーブル（座席在庫テーブル）。
「上映回×座席」の組み合わせごとに1行あり、空席か予約済みかを持つ。

  UNIQUE制約: (f_schedule_id, f_seat_id)
    → 同じ上映回・同じ座席の行はDB上に絶対1つしか存在できない。
      アプリ側のバグでも「同じ席が2行に分かれて2重に空席扱いされる」
      ことがDBレベルで起こり得ない。

予約確定時のトランザクション処理（backend/internal/reservations）：

  1. トランザクション開始（BEGIN）
  2. 予約したい座席を SELECT ... FOR UPDATE で取得
     （GORMの clause.Locking{Strength: "UPDATE"} で実装）
     → この瞬間、対象の座席の行に「排他ロック」がかかる。
       他の予約処理が同時に同じ座席を触ろうとしても、
       このトランザクションが終わるまで"待たされる"。
       ＝同時に2人が「同じ席が空いている」と読んでしまう
       競合状態（レースコンディション）を防ぐ。
  3. 取得できた行数 と 予約したい座席数 を比較
     → 一致しなければ「すでに埋まっている」ということなので
       即エラー（ErrSeatNotAvailable）にしてロールバック
       （＝チャット側では座席選択からやり直しになる）
  4. 一致していれば t_RESERVATION / t_RESERVATION_DETAIL / t_TICKET
     をINSERTし、対象の t_SEAT_STOCK を「予約済み(1)」にUPDATE
  5. すべて成功して初めて COMMIT（1つでも失敗したら全部ロールバック）

イメージ：
  お客さんA「この席で予約したい」→ ロック取得 → 空き確認OK → 予約処理中…
  お客さんB「同じ席で予約したい」→ ロック取得待ち（Aの処理が終わるまで待機）
  Aの処理が完了（COMMIT）→ 席は「予約済み」に変わる
  Bのロックが解放される → Bは「もう空いてない」と正しく判定される
  → 同じ席が2人に売れることは起きない

このロジックはWeb予約（通常の座席選択→決済）とAI予約（チャット内予約）で
完全に同じ関数（CreateReservation）を共通利用しているため、
入口が違っても二重予約対策の強度は変わらない。
